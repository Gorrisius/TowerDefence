# Стінка: розуміємо стан, зв’язки між об’єктами та зміну маршруту

Мета цього уроку — навчитися пояснювати, чому стінка має саме такий стан, як навігація знаходить потрібну перешкоду і чому моб після її руйнування змінює поведінку. Код будемо будувати навколо цих питань. `Final_Solution.md` — повна версія для звіряння після розбору.

## Спочатку розділимо задачу

Уяви конкретний випадок: ти ставиш бетонний блок у клітинку `(4, 2)`. Моб ішов через цю клітинку. Тепер він повинен знайти обхід, а якщо обходу немає — зупинитися, бити саме цей блок і продовжити рух після руйнування.

Для цього потрібні три різні види інформації:

| Питання | Хто знає відповідь |
|---|---|
| Скільки HP залишилося в цьому блоці? | конкретний об’єкт Wall |
| Чи можна пройти через клітинку `(4, 2)` і яка стінка там стоїть? | GridNavigation |
| Куди мені йти та коли завдати наступного удару? | конкретний Enemy |

Wall не шукає шлях за моба. Enemy не змінює словник перешкод самостійно. GridNavigation не зберігає таймер атаки кожного моба. Так кожен клас змінює власний стан, а інші звертаються до нього через методи.

Простеж подію будівництва:

```text
CardPlacement створює Wall
	→ Wall.Initialize отримує клітинку й навігацію
	→ GridNavigation.RegisterWall запам’ятовує перешкоду
	→ моб помічає зміну навігації
	→ моб шукає новий маршрут
```

А тепер подію руйнування:

```text
Enemy викликає Wall.TakeDamage
	→ Wall зменшує власне HP
	→ при нульовому HP просить GridNavigation відкрити клітинку
	→ Wall видаляється
	→ моб помічає зміну й знову шукає маршрут
```

**Перед кодом:** спробуй назвати, який із трьох класів має зберігати HP, маршрут і список перешкод. Якщо всі три речі опиняться в одному класі, кожна зміна бойової логіки зачіпатиме навігацію та стан усіх стінок.

## Крок 3. Розбери й напиши стан `towers/wall/Wall.cs`

Відкрий свій наявний Wall.cs. Зараз у ньому вже є HP, Initialize, TakeDamage і малювання. Розберемо їхній сенс перед наступними змінами.

### 3.1. Що означає `Wall : Node2D`

```csharp
public partial class Wall : Node2D
```

`class Wall` описує тип об’єкта. Дві встановлені стінки — два екземпляри цього типу. Вони мають однакові методи, але окремі значення Health: удар по першій не змінює другу.

`: Node2D` означає успадкування. Wall отримує від Node2D позицію й можливість малювати у 2D. У твоєму файлі зараз стоїть `: Node`; його треба змінити. Node — загальний вузол дерева, а DrawRect і QueueRedraw належать до можливостей CanvasItem, від якого успадкований Node2D.

`partial` дозволяє розділити опис класу між кількома частинами. Godot генерує додаткову частину для інтеграції C# із рушієм. Це не означає, що ти маєш вручну створювати другу половину Wall.

### 3.2. Поле та властивість: чому вони різні

```csharp
[Export] public int MaxHealth { get; set; } = 100;
public int Health { get; private set; }
private GridNavigation _navigation;
```

MaxHealth і Health — **властивості**: get дозволяє прочитати значення, set — присвоїти його. `private set` обмежує присвоєння самим класом Wall. Enemy може прочитати `wall.Health`, але не повинен довільно виконувати `wall.Health = -200`. Для зміни міцності він викликає TakeDamage, де Wall перевіряє допустимість удару.

`[Export]` на MaxHealth дозволяє налаштувати початкову міцність у Godot Inspector. Поточне Health — стан конкретної стінки під час гри. Експорт поточного Health тут не потрібен: Initialize однаково встановлює його з MaxHealth.

`_navigation` — **поле**, яке зберігає посилання на об’єкт GridNavigation. Це не копія мапи. Якщо дві стінки отримали те саме посилання, обидві звертаються до одного контролера навігації. Поле робимо private: його призначає Initialize, іншим класам не потрібно замінювати його посеред бою.

**Простеж приклад:** стінки A і B мають MaxHealth = 100. A отримала 30 шкоди. Тепер A.Health = 70, B.Health = 100, а їхнє посилання на навігацію може бути спільним.

### 3.3. Чому клітинка — Vector2I, а позиція — Vector2

```csharp
public Vector2I Cell { get; private set; }
```

Vector2 містить дробові координати, наприклад позицію моба `(287.4, 161.8)` у пікселях. Vector2I містить цілі координати, наприклад номер клітинки `(4, 2)`.

Клітинка — адреса в сітці. Об’єкт може переміщатися всередині неї, але номер клітинки залишатиметься цілим. У твоєму Wall.cs зараз Cell і параметр cell мають тип Vector2; для індексу сітки зміни обидва на Vector2I.

Ці типи також пояснюють дві функції навігації:

```csharp
public Vector2I WorldCell(Vector2 world) => ...;
public Vector2 CellCenter(Vector2I cell) => ...;
```

Перша повертає **номер клітинки**, друга — **позицію її центру в пікселях**. У твоїй заготовці GridNavigation CellCenter зараз повертає Vector2I — це треба виправити на Vector2, щоб не втрачати сенс і точність світових координат.

### 3.4. Чому перевірка `Cell == null` не підходить

Vector2 і Vector2I — структури, тобто типи значень. Звичайна змінна Vector2I містить координати, а не посилання на об’єкт, тому null не представляє для неї стан «клітинку не задано». Навіть `(0, 0)` може бути цілком нормальною клітинкою.

GridNavigation — клас. Посилання navigation може бути null, якщо контролер не передали. У твоєму Initialize перевіряється `Cell`, хоча це властивість до присвоєння аргументу cell; потрібну придатність клітинки має перевіряти RegisterWall за межами й станом землі.

Якщо перевіряєш navigation вручну, після повідомлення про помилку треба **вийти**:

```csharp
if (navigation == null)
{
	GD.PushError("Navigation is required.");
	return;
}
```

GD.PushError лише повідомляє про проблему. Він не зупиняє виконання методу. Без return наступний рядок усе ще спробує використати null.

### 3.5. Навіщо Initialize і що означає `this`

Сцена Wall знає свій вигляд і MaxHealth. Під час створення вона ще не знає, на якій мапі та в якій клітинці її поставлять. Ці дані передає CardPlacement:

```csharp
public void Initialize(GridNavigation navigation, Vector2I cell)
```

Параметри navigation і cell — вхідні значення лише для цього виклику. Щоб використати їх пізніше в TakeDamage, зберігаємо у стані об’єкта:

```csharp
_navigation = navigation;
Cell = cell;
Health = Math.Max(1, MaxHealth);
_registered = navigation.RegisterWall(cell, this);
```

`Math.Max(1, MaxHealth)` повертає більше з двох чисел. MaxHealth = 100 дає 100; помилкове MaxHealth = 0 дає 1. На початку стінка має бути живою. При отриманні шкоди використаємо нижню межу 0, бо нуль означає руйнування.

`this` означає **цей конкретний екземпляр Wall**. У навігацію передаємо адресу клітинки та посилання на стінку, яка там стоїть. Пізніше моб зможе за клітинкою отримати саме цей об’єкт і викликати його TakeDamage.

RegisterWall повертає bool — відповідь «чи вдалося зареєструвати». `_registered` запам’ятовує цю відповідь. Це не HP: об’єкт може мати додатне HP, але не отримати місце в сітці через зайняту клітинку. У такому випадку готова версія видаляє невдалий екземпляр через QueueFree.

Назву методу в твоєму файлі `Inicialize` виправ на `Initialize`, щоб виклики й оголошення збігалися.

### 3.6. TakeDamage: охоронна умова й зміна стану

Перед відніманням відкинь непридатні виклики:

```csharp
if (!IsAlive || damage <= 0) return;
```

Це раннє повернення. `!` заперечує bool. `||` означає «або»: достатньо будь-якої з умов, щоб вийти. Перевірка damage не дає від’ємній шкоді перетворитися на лікування: `100 - (-20)` стало б 120.

IsAlive об’єднує перевірки стану:

```csharp
public bool IsAlive => _registered && Health > 0 && !IsQueuedForDeletion();
```

`&&` означає «і»: всі умови мають виконатися. `=>` у цій властивості — короткий запис повернення результату виразу. IsAlive обчислюється при читанні, тому не треба окремо синхронізувати ще один прапорець живого стану.

Після перевірки:

```csharp
Health = Math.Max(0, Health - damage);
```

Для Health = 25 і damage = 10 отримаємо 15. Для Health = 5 і damage = 10 отримаємо 0 замість -5.

За нульового HP спочатку RemoveWall відкриває клітинку, потім `_registered = false`, потім QueueFree прибирає вузол. QueueFree виконує видалення наприкінці кадру. До цього моменту інший моб ще може мати посилання на Wall, тому IsAlive уже має повернути false.

### 3.7. Малювання та життєвий цикл

`override` у `_Draw()` означає, що ми задаємо власну поведінку методу, який рушій викликає для малювання CanvasItem. Не викликай `_Draw()` вручну: QueueRedraw повідомляє Godot, що зображення треба оновити.

Ширина зеленої смужки:

```csharp
50f * Health / Math.Max(1, MaxHealth)
```

За 100/100 HP вона має ширину 50. За 50/100 — 25. Літера `f` робить 50 дробовим числом, тому результат може містити дробову частину. У виразі `Health / MaxHealth` з двома int, обчисленому окремо, 50/100 дало б 0 через цілочисельне ділення.

`_ExitTree()` рушій викликає, коли вузол залишає дерево. Якщо Wall ще зареєстрована, треба прибрати її з навігації. Інакше невидимий видалений блок залишить клітинку закритою. `GodotObject.IsInstanceValid` додатково перевіряє існування об’єкта рушія: C#-посилання іноді ще існує після видалення самого Godot-об’єкта.

**Перевір себе:** стінка має 15 HP, два моби в одному кадрі викликають TakeDamage(10). Після першого удару залишиться 5. Після другого — 0, клітинка відкриється, Wall очікуватиме видалення. Третій виклик у цьому кадрі має бути відкинутий. Поясни, яка умова його відкидає.

Тепер звір свою реалізацію з Wall у `Final_Solution.md`. Наступним кроком розберемо, що саме роблять RegisterWall і RemoveWall.

## Крок 4. Розбери структури даних `levels/GridNavigation.cs`

Відкрий свою заготовку GridNavigation. У ній уже є дві сітки та словник. Розберемо, яку задачу вирішує кожна структура.

### 4.1. Dictionary: отримати об’єкт за адресою

```csharp
private readonly Dictionary<Vector2I, Wall> _walls = new();
```

Dictionary<TKey, TValue> зберігає пари «ключ → значення». Тут ключ — координати клітинки, значення — посилання на конкретну Wall:

```text
(4, 2) → стінка A з 70 HP
(7, 2) → стінка B зі 100 HP
```

Коли моб збирається йти у `(4, 2)`, йому треба знайти A. Словник дозволяє запитати її за координатами без перебору всіх стінок. Ключ у словнику унікальний: дві стінки не можуть одночасно отримати однакову адресу.

`new()` створює порожній словник. Компілятор визначає його тип із оголошення зліва. `readonly` забороняє надалі присвоїти полю інший словник; додавати й видаляти записи в існуючому словнику все ще можна.

Чому не вистачить HashSet<Vector2I>? Набір відповідає «ця клітинка зайнята», але не повертає Wall для атаки. Чому не вистачить AStarGrid2D? Сітка знає прохідність точки, але не зберігає HP й метод TakeDamage об’єкта.

### 4.2. TryGetValue та `out`

```csharp
if (_walls.TryGetValue(cell, out Wall wall))
{
	// wall is the object stored at this cell.
}
```

Метод повертає bool: чи є такий ключ. Одночасно через параметр `out` він записує знайдене значення у wall. Якщо ключа немає, тут wall буде null.

Це корисно, бо відсутність стінки — звичайна ситуація. Звернення `_walls[cell]` без перевірки кине виняток, якщо запис відсутній.

WallAt поєднує три перевірки: запис знайдений, Godot-об’єкт існує, стінка жива. Лише тоді повертає Wall, інакше null. Тернарний вираз `condition ? a : b` у розв’язку означає «якщо умова істинна — a, інакше — b».

**Приклад:** WallAt((4, 2)) повертає A. Після RemoveWall для A той самий запит повертає null.

### 4.3. AStarGrid2D: опис можливих переходів

AStarGrid2D — об’єкт Godot для пошуку шляху по сітці. Уяви кожну прохідну клітинку як вершину, а перехід у сусідню клітинку — як ребро. A* шукає послідовність таких переходів до цілі; для вибору напрямку враховує вже пройдену вартість і оцінку залишку до цілі.

Для використання класу нам потрібно правильно задати доступні точки:

```text
Region — межі сітки
DiagonalMode — які переходи дозволені
Update — створення точок за цими налаштуваннями
SetPointSolid — позначення непрохідних точок
```

Solid означає непрохідність **для пошуку шляху**, а не фізичний колайдер.

Для стінки потрібні дві версії прохідності:

| Перешкода | `_grid`: пошук обходу | `_openGrid`: пошук маршруту для пробивання |
|---|---|---|
| Немає землі | закрито | закрито |
| Постійна стіна рівня | закрито | закрито |
| Побудована Wall | закрито | відкрито |

Назва openGrid не означає, що моб може пройти крізь бетон. Це план маршруту, на якому він зустріне руйнівну перешкоду. Зупинку перед нею реалізує Enemy.

### 4.4. Два цикли та межі Rect2I

Region містить Position — початкову клітинку — та Size. End дорівнює Position + Size і є виключеною верхньою межею.

```csharp
for (int y = region.Position.Y; y < region.End.Y; y++)
	for (int x = region.Position.X; x < region.End.X; x++)
	{
		Vector2I cell = new(x, y);
	}
```

За Position = (2, 3), Size = (3, 2) цикл відвідає x = 2, 3, 4 і y = 3, 4 — усього шість клітинок. Знак `<` потрібен, бо координати End уже за межами регіону.

Для кожної клітинки запитай Ground.GetCellSourceId і Walls.GetCellSourceId. Значення -1 означає відсутність тайла. Якщо землі немає **або** є постійна стіна, познач клітинку непрохідною в обох сітках.

У `_Ready()` цей обхід виконується для кожної сітки через `foreach`. На відміну від for, foreach не потребує індексу: він бере черговий об’єкт із колекції. Після побудови сіток зареєструй наявні Wall у Towers і лише тоді запусти спавнер.

### 4.5. Реєстрація — узгоджена зміна двох структур

RegisterWall має повернути bool. Спочатку перевіряє придатність землі та відсутність ключа в словнику. За невдачі повертає false без зміни стану.

За успіху виконує:

```csharp
_walls.Add(cell, wall);
_grid.SetPointSolid(cell, true);
Revision++;
return true;
```

Перший рядок відповідає «хто тут стоїть», другий — «чи можна пройти», третій повідомляє, що попередні маршрути могли застаріти. `++` збільшує число на одиницю.

Якщо оновити лише словник, моб знайде прямий маршрут і натрапить на стінку замість обходу. Якщо оновити лише сітку, пошук обходу працюватиме, але моб не зможе отримати об’єкт для атаки при повному перекритті.

### 4.6. Видалення та ідентичність об’єкта

RemoveWall отримує cell і wall. За cell дістає збережений existing та перевіряє `existing != wall`. Це перевірка відповідності об’єкта: чи видаляє свою реєстрацію саме та стінка, яка зараз займає клітинку.

Після перевірки видаляє запис, відкриває клітинку в `_grid` і збільшує Revision. `_openGrid` змінювати не треба: побудовані стінки там і не блокували точки.

### 4.7. Revision: як помітити зміну без пошуку щокадру

Revision — простий лічильник стану. Наприклад, моб побудував шлях, коли Revision = 3, і запам’ятав 3. Ти поставив стінку: Revision стала 4. На наступному кадрі моб бачить `3 != 4`, перебудовує маршрут і запам’ятовує 4. Поки значення однакові, повторний пошук не потрібен.

Це перевірка актуальності результату. Вона не доводить, що саме цей маршрут змінився: ми свідомо перебудовуємо всі маршрути після зміни мапи, щоб не додавати складніший облік залежностей на цьому етапі.

### 4.8. FindPath та List<Vector2>

List<Vector2> — впорядкований список точок. Порядок важливий: моб спочатку йде до елемента 0, потім до 1 і далі. Dictionary шукає за ключем, а List представляє послідовність руху.

FindPath вибирає сітку за параметром ignorePlayerWalls, перетворює початок і кінець у клітинки, перевіряє межі та прохідність. GetIdPath повертає шлях як координати клітинок. Для руху кожну клітинку перетворюємо у світовий центр і додаємо до List.

Перетворення має три частини:

```text
світова позиція → ToLocal → позиція відносно Ground
локальна позиція → LocalToMap → індекс клітинки
індекс клітинки → MapToLocal → локальний центр → ToGlobal → світовий центр
```

Різні системи координат важливі, якщо Ground зміщений. Індекс `(4, 2)` сам по собі не дорівнює позиції `(4, 2)` пікселів.

**Перевір себе:** у `(4, 2)` поставили Wall, потім зруйнували її. Назви зміни у словнику, обох сітках і Revision на кожній події. Якщо можеш простежити ці зміни, напиши методи та звір із розв’язком.


### 5.3. Напиши RebuildPath

Алгоритм:

```text
запам’ятати поточну Revision
знайти шлях до бази; ігнорувати побудовані стінки тільки для Breaker
якщо звичайний моб не знайшов обхід:
	знайти шлях з ігноруванням побудованих стінок
скинути індекс цілі в 0
```

Ігнорування стінок при пошуку не дозволяє пройти крізь них фізично. Перед входом у їхню клітинку моб зупинятиметься й атакуватиме.

### 5.4. Напиши ReservesCell

Метод повертає true для поточної клітинки живого моба та клітинки його наступної цілі. Контролер будівництва використає це, щоб не поставити стінку на моба або в клітинку, в яку він уже рухається.

### 5.5. Зміни `_PhysicsProcess()`

Дотримуйся цього порядку:

1. Якщо моб мертвий або завершив шлях — вийди.
2. Зменш час до наступного удару на delta, не нижче нуля.
3. Якщо Revision змінилася — виклич RebuildPath.
4. Обчисли доступну відстань руху: Speed × delta.
5. Перед рухом до кожної точки перевір WallAt для її клітинки.
6. Якщо є стінка: за готовності таймера завдай шкоду, встанови затримку AttackInterval і вийди з методу.
7. Якщо стінки немає — рухайся до точки, як у попередній реалізації.
8. Коли непорожній маршрут закінчився — випроміни ReachedBase й видали моба.

Перевірка стінки має стояти **до** MoveToward. Тоді моб атакує із попередньої сусідньої клітинки й не заходить усередину перешкоди.

Після перебудови перша точка — центр поточної клітинки. Моб інколи трохи повернеться до центру, зате не зріже кут. Порожній маршрут означає очікування, а не прибуття на базу.

**Перевірка:** звір і збережи Enemy.cs. Тепер виправимо виклик Setup у спавнері.

### 5.6. Як моб проходить List: шлях і поточний індекс

Нехай шлях містить центри чотирьох клітинок:

```text
_path[0] = A
_path[1] = B
_path[2] = C
_path[3] = D
```

`_targetIndex` — номер точки, до якої моб зараз рухається. Це не координата й не кількість пройдених пікселів. Коли моб досягає B, індекс змінюється з 1 на 2 і наступною ціллю стає C.

`_path.Count` тут дорівнює 4, а допустимі індекси — 0, 1, 2, 3. Саме тому перед зверненням `_path[_targetIndex]` перевіряємо `_targetIndex < _path.Count`. Індекс 4 означає, що всі точки пройдено; читати елемент 4 вже не можна.

Після RebuildPath старий індекс не має сенсу: новий список може містити інші точки та мати іншу довжину. Тому індекс скидається в 0.

### 5.7. Навіщо `delta` і змінна remaining

Speed = 100 означає 100 пікселів за секунду. Один фізичний кадр тривав 0,02 секунди, отже за цей кадр моб може пройти `100 × 0,02 = 2` пікселі. delta передає тривалість кадру.

Якщо рухати моба на 100 пікселів кожен кадр, швидкість залежатиме від кількості кадрів за секунду. Множення на delta задає швидкість у часі.

`remaining` — невикористана відстань руху в поточному кадрі. Якщо до найближчої точки 0,5 пікселя, моб витратить 0,5 і ще матиме 1,5 для наступного відрізка.

Тому в коді є while. Він дозволяє за один кадр пройти кілька коротких відрізків, поки залишилася відстань і є наступна точка. Звичайний if обробив би лише одну точку, а залишок руху загубився б.

У циклі обов’язково має змінюватися стан: після досягнення точки збільшуємо індекс; якщо до точки ще далеко — витрачаємо залишок руху й виходимо. Без цього можна отримати нескінченний цикл.

### 5.8. Таймер удару — окремий стан від руху

`_attackCooldown` зберігає секунди до дозволеного наступного удару. Щокадру:

```csharp
_attackCooldown = Math.Max(0, _attackCooldown - delta);
```

Після удару записуємо AttackInterval. За інтервалу 0,8 і delta = 0,2 значення йдуть так:

| Момент | Cooldown | Чи можна бити |
|---|---|---|
| Після удару | 0,8 | ні |
| Через один кадр | 0,6 | ні |
| Через два | 0,4 | ні |
| Через три | 0,2 | ні |
| Через чотири | приблизно 0 | так |

Для дробових чисел у реальній грі можливі невеликі похибки; Math.Max прибирає від’ємний залишок. Початкове значення 0 дозволяє перший удар одразу. Ми не створюємо окремий Timer на кожний удар: для цієї логіки вистачає поля стану моба.

Після обробки стінки `return` завершує поточний `_PhysicsProcess`, тому залишок руху не витрачається на проникнення в бетон. На наступному кадрі таймер зменшиться, а перевірка повториться.

### 5.9. Повний перекритий прохід: простеж вручну

```text
A → B → Wall → D → Base
```

Обходу немає. Пошук у `_grid` повертає порожній список, тому RebuildPath пробує `_openGrid` і знаходить цей маршрут. Моб проходить A й B. Перед наступним переходом WallAt повертає стінку — моб зупиняється в B.

Він б’є, поки Wall не відкриє клітинку. Revision змінюється. На наступному кадрі RebuildPath уже може знайти маршрут у звичайній `_grid`. Лише після цього моб продовжує рух.

Якщо навіть `_openGrid` не має шляху, проблема в постійній геометрії. Тому завершення перевіряє і `_path.Count > 0`, і вичерпання індексу. Інакше порожній список із індексом 0 помилково означав би «моб уже пройшов усе й досяг бази».

### 5.10. Сигнал: як повідомити про прибуття без знання спавнера

Enemy визначає сигнал ReachedBase й випромінює його після завершення маршруту. EnemySpawner підписується на цей сигнал та збільшує власний лічильник прибуттів.

Це дозволяє Enemy повідомити про подію без зберігання посилання на конкретний спавнер. `enemy.ReachedBase += OnEnemyReachedBase` підписує обробник; `EmitSignal(SignalName.ReachedBase)` запускає підписані обробники.

**Перевір себе:** у B до стінки ще один крок, remaining = 20, cooldown = 0,3. WallAt знайшов живу стінку. Моб не рухається й не б’є: таймер ще не готовий. Коли cooldown стане 0, він завдасть удару, але все одно залишиться в B. Поясни, чому навіть велике remaining не дозволяє пройти перешкоду.

TowerCardData успадковує Resource. Resource зберігає **дані**: назву, ціну, зображення й посилання на сцену. Його файл — `.tres`.

```text
wall.tres → опис картки
wall.tscn → шаблон стінки
Instantiate() → конкретна стінка A на мапі
Instantiate() ще раз → інша стінка B
```

BlocksPath описує властивість споруди, яку створює картка: вона змінює прохідність. Це поле дозволяє контролеру вибрати правило розміщення, не перевіряючи назву Title. Назву можна змінити чи перекласти — правило має залишитися тим самим.

```text
прибрати вибір і прев’ю
оновити руку
```

TreeExited потрібен, щоб зруйнована стінка не залишала клітинку зайнятою в контролері будівництва. Сама Wall окремо відкриває прохід у навігації.

Збережи файл і натисни Build.

**Перевірка:** компіляція успішна. До запуску залишилося додати картку в руку.

### 10.5. HashSet, підписка на подію та захоплення `cell`

`_occupied` має тип HashSet<Vector2I>. Це набір унікальних адрес. Він потрібен для швидкої відповіді «чи є тут уже споруда», включно з турелями, які не зберігаються в словнику руйнівних стінок.

Додавання клітинки при будівництві — лише половина роботи. При видаленні споруди адресу треба прибрати:

```csharp
tower.TreeExited += () => _occupied.Remove(cell);
```

TreeExited — подія виходу вузла з дерева. `+=` додає обробник. `() => ...` — лямбда: невелика функція без параметрів, яку викличуть **пізніше**, коли відбудеться подія. Це не той самий `=>`, що ми бачили у властивості: тут він записує функцію.

Функція запам’ятовує локальну змінну cell із цього виклику TryPlaceAt. Це називається захопленням змінної. Кожне будівництво має власний виклик методу й власний cell: видалення споруди в `(4, 2)` прибере `(4, 2)`, а не клітинку, на яку гравець наведе мишу пізніше.

Чому Wall.RemoveWall не може замінити цю підписку? Він очищає навігацію, а `_occupied` належить CardPlacement. Це два споживачі стану: одному потрібна прохідність, іншому — доступність місця для будівництва.

### 10.6. Перевірка типу через `is`

Instantiate повертає загальний Node, бо шаблон сцени може мати будь-який корінь. Контролеру потрібен Node2D для позиції, а стінці — Wall для Initialize.

```csharp
if (tower is Wall wall)
{
	wall.Initialize(_navigation, cell);
}
```

`is Wall wall` одночасно перевіряє фактичний тип об’єкта й дає змінну wall з цим типом. Турель залишиться Node2D і не виконає цей блок. Це не створює нову стінку; tower і wall посилаються на той самий екземпляр.

Для BlocksPath-картки тип Wall є обов’язковим. Якщо в Inspector помилково призначили сцену турелі, перевірка має завершити встановлення до списання енергії.

### 10.7. Порядок дій визначає поведінку

Спочатку встановлюємо позицію і додаємо вузол у Towers. Потім Initialize передає готовому об’єкту залежності й реєструє клітинку. Після успішних перевірок контролер оновлює енергію та стан копії картки.

При AddChild вузол входить у дерево й може отримати `_Ready()`. У нашої Wall початкові HP задає Initialize, тому не перенось залежні від навігації дії у `_Ready()` без зміни порядку ініціалізації.

Для заздалегідь розміщених стінок порядок інший: Godot викликає `_Ready()` дітей раніше за `_Ready()` батьківського GridNavigation. Саме тому їх реєструє батько **після** створення сітки. Інакше дочірня стінка могла б звернутися до ще неготової навігації.

**Перевір себе:** після руйнування моби проходять крізь клітинку, але нова картка каже «зайнято». Де шукаємо проблему? У `_occupied` та TreeExited, бо навігація вже відкрила шлях. Якщо картку можна поставити, але моби обходять невидимий блок — перевіряємо RemoveWall і `_grid`.

## Крок 11. Налаштуй руку на рівні

1. Відкрий `res://levels/level_cards.tscn`.
2. Вибери CardPlacement.
3. У StartingHand постав три елементи: `machine_gun.tres`, `wall.tres`, `wall.tres`.
4. У StartingEnergy постав `6`.
5. Вибери `CardPlacement/HUD/HandPanel`. У Layout зміни Offset Left на `-480`; Offset Right залиш `-16`.
6. Вибери дочірній Hand і зміни Offset Right на `452`.
7. Для EnergyLabel і StatusLabel також постав Offset Right = `452`.
8. Збережи рівень.

Три кнопки по 140 пікселів і два проміжки по 10 займають 440 пікселів. Тому панель розширили перед запуском. Два посилання на wall.tres — дві копії картки в руці: використання однієї не витратить другу.

**Перевірка:** у StartingHand три ресурси, панель має достатню ширину, рівень збережений.

## Крок 12. Перевір установлення та обхід

Запусти відкритий рівень через F6.

1. Вибери картку стінки. На мапі має з’явитися прев’ю.
2. Наведи на постійну стіну або зайняту клітинку — прев’ю має стати червоним.
3. Постав стінку на вільному проході, де є можливість обійти її.
4. Перевір: енергія зменшилася з 6 до 5, використана копія затемнилася, на мапі з’явилася стінка зі смужкою HP.
5. Простеж за мобами: вони мають піти в обхід.

Якщо стінка будується лише на BuildZones, перевір Blocks Path у ресурсі та перевірку цього поля в CanPlaceAt. Якщо моби йдуть старим маршрутом, перевір Initialize при будівництві й порівняння Revision у Enemy.

## Крок 13. Перевір атаки та руйнування

Зупини гру. Для цього тесту потрібно перекрити прохід повністю. Якщо на твоїй мапі він ширший за дві клітинки, додай у StartingHand достатньо копій wall.tres і збільш StartingEnergy. Для великої руки також розшир панель; простіше тестувати на вузькому проході.

Запусти рівень знову:

1. Перекрий прохід стінками, не ставлячи їх на зайняті мобами клітинки.
2. Моб має зупинитися перед перешкодою та бити її.
3. HP має зменшуватися на 10 за удар із затримкою 0,8 секунди; перший удар відбувається одразу.
4. Після нульового HP стінка має зникнути, а моб — продовжити рух за оновленим маршрутом.
5. Якщо залишилася невикористана копія картки й енергія, перевір можливість побудувати нову стінку на звільненій клітинці після проходу моба.

Витрачена енергія й зіграна картка після руйнування не повертаються.

Якщо стінка зникла, але моб стоїть, перевір RemoveWall і зміну Revision. Якщо клітинка назавжди зайнята для будівництва — перевір підписку TreeExited у CardPlacement.

## Крок 14. Перевір сумісність із туреллю

Перезапусти рівень і встанови кулемет на BuildZones. Він має стріляти по мобах, як раніше. Моб, якого знищила турель, має припинити рух і атаки стінки.

Після цього основний урок завершений: стінка створюється карткою, змінює маршрут, отримує шкоду та звільняє прохід після руйнування.

## Додаткова перевірка: Breaker

Роби її після основного уроку. Зупини гру, відкрий сцену ворога, яку використовує EnemySpawner, і тимчасово ввімкни IsBreaker на корені. Запусти рівень та постав стінку на прямому маршруті, залишивши обхід. Такий моб має атакувати стінку замість обходу. Після тесту поверни IsBreaker у false для звичайного ворога.

Окремі хвилі Breaker налаштовуватимемо окремо. Поточний пошук через стінки вибирає найкоротший геометричний маршрут, а не маршрут із найменшою сумою HP перешкод.
